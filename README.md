# Autoshop Takumi — Bilingual Vehicle Sales Website

A bilingual (Japanese/English) vehicle sales website for Autoshop Takumi, built as a reusable template for other dealerships. Visitors can browse and filter inventory in either language; non-technical staff manage all content — including site-wide contact info and social links — from a generated admin dashboard, no code changes required.

---

## Stack

| Layer | Technology |
|---|---|
| Framework | Next.js 15 (App Router, React Server Components) |
| CMS / Admin | Payload CMS 3.x (embedded in the Next.js app) |
| Database | SQLite (local dev) → PostgreSQL/Neon (production, wired via `DATABASE_URI` — see [Environment Variables](#environment-variables)) |
| Image storage | Local `/public` (dev) → Cloudflare R2 (production, wired via `R2_*` vars — falls back to local storage if unset) |
| UI | Tailwind CSS v4 + custom CSS-variable brand tokens |
| i18n (static UI) | next-intl (`/ja/...`, `/en/...` URL routing) |
| i18n (content) | Payload field-level localization (JA + EN per field) |
| Email | Resend (inquiry notifications) — coded, needs `RESEND_API_KEY` to activate |
| Tests | Vitest + React Testing Library (component) · Playwright (e2e: admin UI, public site, REST API) |
| Hosting | Vercel (planned) |

## What's Built

### Public site

| Page | Route | Description |
|---|---|---|
| Landing | `/[locale]` | Hero, featured vehicles, "Why Choose Us" trust signals — all from the `Homepage` global |
| Vehicle listing | `/[locale]/vehicles` | Filterable + sortable grid; filters: make, model, body type, transmission; sort: newest / price asc / price desc |
| Vehicle detail | `/[locale]/vehicles/[slug]` | Photo gallery, highlights list, flexible spec table, inquiry form, related vehicles |
| About | `/[locale]/about` | Bilingual company story, services grid, company profile table, embedded map — all sourced from `SiteSettings`, not hardcoded |

**Header / Footer**, present on every public page:
- Logo, nav (Home / Inventory / About), locale switcher (JA/EN), light/dark theme toggle
- Instagram follow link — only renders if a `socialLinks` entry with `platform: 'instagram'` exists in `SiteSettings`
- Footer contact block (phone, email, address) — all read live from `SiteSettings`, not hardcoded in components

The language switcher swaps both the UI chrome and the vehicle content (titles, descriptions, spec rows) simultaneously. URLs are locale-prefixed so both versions are independently linkable and indexable.

**Theming**: a `data-theme="light"|"dark"` attribute on `<html>`, set by an inline script before paint (avoids flash-of-wrong-theme) and toggled client-side. The choice is persisted to `localStorage` only when the user actually clicks the toggle — an inferred system-preference theme on first visit is not persisted, so the site keeps following OS theme changes until the visitor makes an explicit choice.

### Admin dashboard (`/admin`)

Entirely auto-generated by Payload CMS from the schema in `payload.config.ts` — no bespoke admin screens were written:

- **Vehicles** — full CRUD, bilingual field tabs (JA/EN), image upload, gallery reorder. A `beforeChange` hook blocks setting `status: 'available'` without a `heroImage`; drafts can be saved without one.
- **Makes / Models** — editable taxonomy; adding a new make/model here immediately makes it available as a listing-page filter with no redeploy.
- **Media** — image library with automatic resizing to size variants on upload.
- **Inquiries** — inbox of contact-form submissions with New/Contacted/Closed status tracking.
- **Site Settings** — shop name, logo, contact email/phone, address, **social links** (Instagram etc., used by Header/Footer/About), inquiry notification recipients, `showSoldVehicles` toggle, default SEO title/description.
- **Homepage** — hero copy/image, featured vehicle picks, "Why Choose Us" trust signal points — all editable without a deploy.
- **Users** — auth collection, `admin`/`editor` roles. Editors can read their own user record only; admins can read/manage all users.

## API Reference

Every collection and global gets a REST API automatically from Payload — there are no custom API route handlers in this project (the earlier `src/app/api/inquiries/route.ts` custom endpoint was removed; inquiry submission now goes straight through Payload's own `/api/inquiries` collection endpoint). All REST traffic is handled by the single catch-all at `src/app/(payload)/api/[...slug]/route.ts`.

**Auth requirement column reflects a collection/global's own `access` config. If a collection has no `access` block at all, Payload's default (`Boolean(req.user)`) applies — every operation, including reads, requires a logged-in user.** This was verified against the running dev server, not assumed from source alone.

| Collection / Global | Endpoint | Read | Create | Update | Delete |
|---|---|---|---|---|---|
| Vehicles | `/api/vehicles` | Public — but only `available`/`reserved`/`sold`; drafts require auth | Auth | Auth | Auth |
| Makes | `/api/makes` | **Auth required** (no `access` block → default) | Auth | Auth | Auth |
| Models | `/api/models` | **Auth required** (no `access` block → default) | Auth | Auth | Auth |
| Media | `/api/media` | **Auth required** (no `access` block → default) | Auth | Auth | Auth |
| Inquiries | `/api/inquiries` | Auth | **Public** (form submissions) | Auth | Admin only |
| Users | `/api/users` | Admin: all · Editor: self only | Admin | Admin | Admin |
| SiteSettings (global) | `/api/globals/site-settings` | **Auth required** (no `access` block → default) | — | Auth | — |
| Homepage (global) | `/api/globals/homepage` | **Auth required** (no `access` block → default) | — | Auth | — |

Plus Payload's standard auth endpoints for the `Users` collection: `POST /api/users/login`, `POST /api/users/logout`, `GET /api/users/me` (always 200, returns `{user: null}` when unauthenticated — doesn't itself require auth).

**Why the public site still works despite Makes/Models/Media/SiteSettings/Homepage being auth-gated:** none of the public pages call these REST endpoints from the browser. Server Components fetch this data server-side through Payload's **Local API** (`payload.find()` / `payload.findGlobal()` in `src/lib/payload.ts` and `src/lib/site-settings.ts`), which defaults to `overrideAccess: true` and bypasses access control entirely. The REST endpoints above are effectively admin/internal-tooling surfaces, not part of the public site's actual data path — a distinction worth knowing before assuming "the content shows up publicly" implies "the API is public."

An earlier version of `e2e/api.spec.ts` had two tests (`GET /api/globals/site-settings`, `GET /api/media`) incorrectly asserting these are publicly readable — they passed only because of an unrelated Playwright bug where `playwright.request.newContext()` was silently inheriting the admin session instead of being anonymous. Both are fixed to assert the real (403) behavior.

## Architecture Notes

- **Dynamic rendering is required, not optional, on the public locale layout.** `src/app/(public)/[locale]/layout.tsx` declares `generateStaticParams()` for the two locales; combined with `getSiteSettings()` calling no dynamic API on its own, Next.js would otherwise be free to statically cache the layout's render — meaning Header/Footer content could get frozen at whatever `SiteSettings` looked like at first build/request, silently ignoring later admin edits. `export const dynamic = 'force-dynamic'` on that file exists specifically to prevent this.
- **CMS-driven, not hardcoded, shop identity.** Contact info and social links live in `SiteSettings` and are read via `src/lib/site-settings.ts`'s `getSiteSettings(locale)` helper, passed down from the locale layout into `Header`/`Footer`. Adding a new social platform or changing the phone number needs zero code changes.
- **Localized-required-field ordering matters on first write.** `payload.config.ts` sets `defaultLocale: 'ja'`. For a field that's both `required: true` and `localized: true` (e.g. `Homepage.whyUsPoints[].heading`), Payload validates against the default locale on the document's first creation — writing the non-default locale (`en`) first with the default locale (`ja`) left empty will fail validation. `scripts/seed.ts` writes `ja` first for exactly this reason.

## Design System (as implemented)

The "Typography" and status-badge-as-CSS-token ideas from an earlier draft of this doc were never actually implemented — this section describes what's real in the codebase today.

### Color tokens

All colors live as bare `H S% L%` triples in `src/app/globals.css`, consumed as `hsl(var(--token))`. Retheming means editing this file only — component code never hardcodes colors.

| Token | Light | Dark | Use |
|---|---|---|---|
| `--primary` | `hsl(18 99% 50%)` / `#fe4d03` | same | Primary actions, active nav state, accents |
| `--secondary` | `hsl(213 50% 23%)` / `#1D3557` | same | Footer background, secondary emphasis |
| `--background` / `--foreground` | white / near-black | near-black / near-white | Page background/text |
| `--card` / `--card-foreground` | white / near-black | dark surface / near-white | Card surfaces |
| `--muted` / `--muted-foreground` | light gray / gray | dark gray / lighter gray | Secondary surfaces, subdued text |
| `--border` | light gray | dark gray | Borders/dividers |
| `--nav-bg` / `--nav-fg` / `--nav-border` | white / near-black / light gray | dark / near-white / dark gray | Header specifically |

Dark mode is `[data-theme="dark"]` on `<html>`, same token names, different values — component code is identical in both modes.

### Typography

No custom fonts are wired up (no `next/font`, no `font-family` overrides anywhere in `src/`) — the site currently renders in the browser/Tailwind default sans-serif stack for both locales. Custom display/body fonts remain a real gap if brand fidelity matters before launch.

### Status badges

Implemented as plain Tailwind utility classes in `VehicleCard.tsx` (`bg-green-100 text-green-800` for available, amber for reserved, gray for sold) rather than CSS-variable tokens — the one place color isn't centralized through `globals.css`. Worth revisiting if a second-shop retheme ever needs different status colors.

## Testing

- **Component tests** (Vitest + Testing Library): `npm test` — VehicleCard, LocaleSwitcher, utils
- **Type check**: `npx tsc --noEmit`
- **E2E tests** (Playwright, requires the dev server running): `npm run test:e2e` — `e2e/admin.spec.ts` (admin CRUD + styling regression guards), `e2e/api.spec.ts` (REST behavior + access control), `e2e/public.spec.ts` (visitor-facing pages, filters, theming)

CI (`.github/workflows/ci.yml`) runs all of the above on every PR to `master`, plus a production build check, before allowing a merge. See `CLAUDE.md` for the full git/PR/testing workflow this repo follows.

### Visual regression tests

A second, independent Playwright project/config (`playwright.visual.config.ts`) covers screenshot-based visual regression coverage for the public site and the Payload admin — the specific check that catches a page rendering blank or badly broken (the failure class behind the incident in PR #14). It's deliberately kept separate from the functional suite above: different config file, different CI job (`visual-e2e`), its own job-local database, and no shared setup code with `e2e/global-setup.ts`/the `chromium` project — running `npm test`, `npx tsc --noEmit`, or `npm run test:e2e` is unaffected by any of this.

- **Run locally, for iteration**: `npm run test:e2e:visual` — runs the `visual` project only, against whatever's already in your local database. Useful for checking a page's rendering while developing, but **local screenshots are never valid baselines** — see below.
- **`visual-first-run` is CI-only.** It exercises `/admin/create-first-user`, which only renders correctly against a genuinely empty, no-admin-user database — the `visual-e2e` CI job's own job-local database, created fresh on every run. There's no equivalent way to reset your local dev database into that exact state on demand, so this project isn't meant to be run locally.
- **Why local baselines don't work — font/OS rendering determinism**: screenshot comparison is inherently sensitive to font rendering, subpixel anti-aliasing, and OS-level rendering differences — a well-known Playwright limitation, not specific to this project. A screenshot taken on a developer's own machine (macOS, Windows, or even a different Linux distro/version) will show diffs against a baseline generated on CI even with zero actual visual change. For that reason, this repo treats **CI's `ubuntu-24.04` runner label** (not the floating `ubuntu-latest` alias other jobs use, which can jump between entire OS major versions over time) as the *only* environment baselines are authoritative for. `npx playwright test --config=playwright.visual.config.ts --update-snapshots` still works locally for quick debugging of a specific diff, but its output should never be committed.
- **Updating a baseline after an intentional design change**: from the GitHub Actions tab, manually run the **Update Visual Baselines** workflow (`update-visual-baselines` job in `ci.yml`, triggered via `workflow_dispatch`) against your PR's branch. It regenerates every baseline PNG on the pinned `ubuntu-24.04` runner and commits them directly back to that branch (via `stefanzweifel/git-auto-commit-action`, scoped to only the two snapshot directories). This is the one and only publication mechanism — there's no artifact-download-and-manually-commit alternative.
- **Structured results (Allure)**: every Playwright invocation (`test:e2e` and `test:e2e:visual`, locally and in CI) writes `allure-results/` via the `allure-playwright` reporter. Generate a local, human-browsable HTML report with `npm run allure:report`, then open it with `npx allure open allure-report`. In CI, each of the `e2e` and `visual-e2e` jobs uploads its own `allure-results`/`allure-report` as a build artifact (`allure-results` and `allure-results-visual` respectively) — find them on that workflow run's Summary page, downloadable regardless of pass/fail. This is also the structured-results format the (separately tracked) future test-results dashboard issue is designed to consume.

## Local Development

**Prerequisites:** Node 22+ (Node 20 is past its supported LTS window as of this writing; CI's e2e job still pins `node-version: 20` and is worth updating). No other accounts needed for local dev.

```bash
# 1. Clone and install
git clone https://github.com/chamirusenarath96/autoshop-takumi.git
cd autoshop-takumi
npm install   # .npmrc sets legacy-peer-deps=true, so no flag needed — see Known Issues

# 2. Set up environment
cp .env.example .env
# Edit .env: set PAYLOAD_SECRET to any random string

# 3. Start dev server (SQLite database is created automatically)
npm run dev
# → http://localhost:3000       public site
# → http://localhost:3000/admin  admin dashboard

# 4. (Optional) Seed sample data
npm run seed
```

On first visit to `/admin`, Payload will prompt you to create the first admin user.

## Known Issues / Gotchas

- **`npm run seed` and `npm run seed:e2e` fail on Node — but only when invoked directly via `tsx`.** `payload@3.85.1`'s `dist/bin/loadEnv.js` does `const { loadEnvConfig } = nextEnvImport` after a default import of `@next/env`. `@next/env`'s bundled CJS output sets `__esModule: true` without an actual `default` export. Node's native ESM loader (used by `npm run dev`/`npm run build`) tolerates this fine; `tsx`'s CJS-compatibility transform does not, and throws `Cannot destructure property 'loadEnvConfig' of 'import_env.default' as it is undefined`. Confirmed to reproduce identically across Node 22 and Node 24, and across Windows/WSL — it's a genuine upstream `payload`/`@next/env` version incompatibility, not an environment issue. A `node_modules` patch was tried and reverted: it fixed `tsx` but broke the real Next.js dev server (which needs the original `import` syntax, since it has no `require` in true ESM). No clean fix has been applied yet — see the corresponding roadmap/backlog item.
- **CI's e2e job pins Node 20** (`.github/workflows/ci.yml`), which is now past its LTS support window. Other jobs may differ — worth auditing for consistency.
- There's a `graphql` version mismatch between the root project and `@payloadcms/graphql` that makes plain `npm install` fail peer-dependency resolution. Fixed via `.npmrc` (`legacy-peer-deps=true`) so it's automatic everywhere — local dev, CI, and Vercel builds — no flag needed. (This is also what broke the first production deploy: Vercel's build runs `npm install` with no flags, and hit this before `.npmrc` was added.)

## Environment Variables

```bash
# Required
NEXT_PUBLIC_SITE_URL=http://localhost:3000
PAYLOAD_SECRET=                    # Any random secret string

# Production: PostgreSQL (Neon recommended) — set this to switch payload.config.ts
# from SQLite to postgresAdapter automatically. Unset = SQLite, as in local dev.
DATABASE_URI=postgres://user:pass@host/db?sslmode=require

# Production: Cloudflare R2 image storage — set ALL FIVE to activate the
# s3Storage plugin on the media collection. Any one missing = falls back to
# local /public/media, same as local dev.
R2_BUCKET=
R2_ENDPOINT=                       # https://<account>.r2.cloudflarestorage.com
R2_ACCESS_KEY_ID=
R2_SECRET_ACCESS_KEY=
R2_PUBLIC_URL=                     # Public bucket URL

# Production: Resend email (inquiry notifications) — hook is coded, needs these to activate
RESEND_API_KEY=
NOTIFY_EMAIL_FROM=inquiries@autoshoptakumi.example
NOTIFY_EMAIL_TO=staff@autoshoptakumi.example
```

Local dev works with only `PAYLOAD_SECRET` set. All other variables are production-only. Postgres, R2, and Resend are all wired to activate automatically the moment their env vars are present — no code changes needed at deploy time, just setting them in Vercel project settings. The switch logic lives in `src/lib/deploymentConfig.ts` (unit-tested in `src/lib/__tests__/deploymentConfig.test.ts`) and is consumed by `payload.config.ts`.

## Production Deployment (Vercel)

1. Create accounts: [Neon](https://neon.tech) (Postgres), [Cloudflare R2](https://developers.cloudflare.com/r2/) (storage), [Resend](https://resend.com) (email)
2. Connect this GitHub repo to a new Vercel project (Vercel dashboard → Add New Project → Import Git Repository — this step needs to happen in the dashboard so Vercel's GitHub App gets the OAuth grant it needs to auto-deploy on push)
3. Add all environment variables from the block above in Vercel project settings — `payload.config.ts` picks up Postgres/R2/Resend automatically the moment they're set, no further code changes needed
4. Push to `master` — CI runs, then Vercel auto-deploys

## Reusing as a Template (Shop #2)

Because shop identity (contact info, social links, hero copy, taxonomy) lives in Payload data rather than component code, a second shop is stood up by:

1. Fork this repo
2. Point it at a new database and R2 bucket (new env vars)
3. Update the brand tokens in `src/app/globals.css`
4. Seed new `SiteSettings` (shop name, logo, contact info, social links) and `Makes`/`Models` taxonomy
5. Deploy

No page templates, filter logic, or admin screens need to be rewritten.
