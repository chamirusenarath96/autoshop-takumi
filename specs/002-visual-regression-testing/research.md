# Phase 0 Research: Visual/UI Regression Testing with Allure Reporting

All items below were determined from the source issue's explicit proposal plus inspection of this repo's existing `playwright.config.ts`, `.github/workflows/ci.yml`, and `e2e/*.spec.ts` conventions — no items remained `NEEDS CLARIFICATION` after spec authoring, so this file records the reasoning behind each Technical Context decision rather than resolving open questions.

## Decision: Visual comparison mechanism

**Decision**: Use Playwright's native `expect(page).toHaveScreenshot()` / `expect(locator).toHaveScreenshot()`.

**Rationale**: Already bundled with `@playwright/test`, which this project already depends on and already uses for all other e2e coverage. Produces pixel-diff PNGs on failure automatically, integrates with the existing `html`/`github` reporters, and needs no new test runner or CI step beyond what already exists for the functional suite. The source issue explicitly calls this out as the preferred approach over adopting a separate framework.

**Alternatives considered**:
- **Percy / Chromatic (paid SaaS)**: Rejected per the source issue and spec Assumptions — external cost/vendor dependency for a capability Playwright already provides natively.
- **A custom pixel-diff script (e.g., `pixelmatch` invoked manually)**: Rejected — reinvents what `toHaveScreenshot()` already does, with worse reporter/CI integration.

## Decision: Test organization — separate Playwright `project`

**Decision**: `visual` and `visual-first-run` are Playwright projects defined in a **new, second config file**, `playwright.visual.config.ts` — not added to the existing `playwright.config.ts`'s `projects` array — with visual assertions in new `e2e/visual.spec.ts`/`e2e/visual-first-run.spec.ts` files (not mixed into `admin.spec.ts`/`public.spec.ts`). `playwright.visual.config.ts` sets no `globalSetup` at all (see the Isolation-model decision below for why this is required, not optional). The existing `playwright.config.ts` (still just the one `chromium` project) gets `testIgnore` for **both** new spec files, so its file discovery never picks them up regardless of which config a given `npx playwright test` invocation uses. `package.json`'s `test:e2e` script stays `playwright test` (implicitly using `playwright.config.ts`, its default config file — Playwright only looks at one config file per invocation unless `--config` is passed, so an un-flagged `test:e2e` naturally can't reach the visual config's projects at all); a new `test:e2e:visual` script (`playwright test --config=playwright.visual.config.ts --project=visual`) covers the `visual` project, and `visual-first-run` is documented as CI-only via the `visual-e2e` job, invoked directly with `--config=playwright.visual.config.ts --project=visual-first-run` (see quickstart.md).

**Rationale**: Playwright projects can be filtered independently, get separate result grouping in reporters (including Allure, which reports Playwright project as a distinct dimension), and can have distinct `use` config (e.g., forcing consistent `deviceScaleFactor`/color-scheme for visual tests specifically) without affecting the `chromium` functional project. This directly satisfies FR-005 (distinct, separately-triageable group) using a mechanism already native to the tool in use, consistent with Constitution Principle VI (no premature abstraction). Splitting into two config files, not just two `projects` entries in one file, turned out to be required rather than a style preference once the `globalSetup` constraint below was identified — Playwright's `globalSetup` is a single top-level config property that runs before *every* project a given config file defines, with no per-project opt-out, so `visual-first-run` can only ever see a genuinely empty database if it's governed by a config file that never declares `globalSetup` in the first place.

**Alternatives considered**:
- **A single config file with a runtime "visual mode" env-var flag inside `e2e/global-setup.ts`** that makes it a no-op when set (e.g. `if (process.env.PLAYWRIGHT_VISUAL_MODE) return`): Rejected — this would require modifying `e2e/global-setup.ts`, undermining the "zero changes to existing test infrastructure" property the Isolation-model decision is built around; a second config file that simply never references `global-setup.ts` needs no such modification.
- **Tagging tests with `test.describe` + grep filters** (no new project): Rejected — grep-based filtering is more fragile (relies on naming discipline) and doesn't get separate reporter grouping the way `project` does, and doesn't address the `globalSetup` problem at all.
- **Leaving `chromium` without `testIgnore` for the new spec files**, relying on the two separate config files' own `testDir`/project scoping alone: Rejected — a defense-in-depth choice, not strictly required once the configs are separate, but cheap insurance against a future change that points `playwright.config.ts` at a broader `testDir` or adds a catch-all project.

## Decision: Isolation model — visual tests get their own CI job and database

**Decision**: `visual` and `visual-first-run` (Playwright projects defined in `playwright.visual.config.ts`, per the previous decision — critically, a config file with **no `globalSetup`**) run in a **new, dedicated CI job** (`visual-e2e` in `.github/workflows/ci.yml`), entirely separate from the existing `e2e` job, against a **freshly created, job-local SQLite database file** (a distinct `DATABASE_URI` env var, not shared with the `e2e` job) and its own `npm run dev` server instance. This job does **not** modify `e2e/global-setup.ts` or the `chromium` project's test definitions in any way — those stay exactly as they are today (the `e2e` job/`playwright.config.ts` do still gain the Allure reporter and a results-upload step, per the Structured-results decision below — those are additive tooling changes, not changes to `chromium`'s tests or their pass/fail behavior). Because `playwright.visual.config.ts` deliberately has no `webServer` entry (per the previous decision), the job manages the dev server's lifecycle itself as an explicit step: start `npm run dev` in the background (`&`, capturing its PID) with the job-local `DATABASE_URI`, poll the server (e.g. `npx wait-on http://localhost:3000` or an equivalent readiness loop) before proceeding to step 1 below, and stop the server in a step gated on `if: always()` at the end of the job so it's cleaned up even if an earlier step fails. Within `visual-e2e`, in order:
1. `npx playwright test --config=playwright.visual.config.ts --project=visual-first-run` runs first, directly, against the still-empty fresh database. Because this invocation uses `playwright.visual.config.ts` — which never references `e2e/global-setup.ts` — no admin user exists yet, so `/admin/create-first-user` genuinely renders its first-run form rather than redirecting.
2. A small setup script, `e2e/visual-setup.ts` (run as a plain step in the CI job — a script, not a Playwright `globalSetup`), then: creates the admin user and writes `AUTH_STATE_PATH` (the same login/create-first-user branching logic `e2e/global-setup.ts` already has), seeds `SiteSettings` with the same fields `global-setup.ts` seeds today (shop name, contact email/phone, address, Instagram link — so Header/Footer/About render real content, not empty CMS fields), and creates the one deterministic Make/Model/Vehicle fixture (see the fixture decision below).
3. `npx playwright test --config=playwright.visual.config.ts --project=visual` then runs against this now-seeded, still job-isolated database.

**Rationale**: Two earlier drafts of this decision each missed a different way the "shared state" problem actually manifests. The first tried reusing the existing `e2e` job/database via Playwright's project-dependencies model (an `admin-setup` project that `chromium`/`visual` depend on, `visual-first-run` opting out) — review correctly identified that doesn't *guarantee* an empty database (the absence of a dependency edge doesn't stop some other project from having already created a user) and doesn't stop the `chromium` project's own functional-test fixtures from making the listing snapshot non-deterministic. The second draft moved to a dedicated job with its own database, which fixes both of those — but still assumed putting `visual`/`visual-first-run` in `playwright.config.ts`'s existing `projects` array would let `visual-first-run` skip admin creation; review correctly caught that `globalSetup` is a single top-level config property that Playwright runs before *every* project a config file defines, with **no per-project override**, so `visual-first-run` would still have seen `e2e/global-setup.ts` create a user first regardless of which CI job invoked it. Only removing `globalSetup` from the config file `visual-first-run` uses at all — hence the separate `playwright.visual.config.ts` — actually closes this gap. Combined, a dedicated job (fresh database) *and* a `globalSetup`-free config file (no forced admin creation) together make both "empty until step 2 creates a user" and "contains exactly the one seeded vehicle" structurally true, not merely likely.

**Alternatives considered**:
- **Project-dependencies within the existing shared `e2e` job/database** (the first rejected draft): Doesn't actually guarantee the empty-DB precondition or listing-page determinism — see Rationale.
- **A single config file with `visual`/`visual-first-run` in `playwright.config.ts`'s `projects` array** (the second rejected draft): Still runs `globalSetup` before `visual-first-run` regardless of dedicated-job database isolation — see Rationale and the Test-organization decision above.
- **A dedicated Docker container per test run**: Rejected as disproportionate — a second CI job with a second SQLite file uses infrastructure this project already has (the `e2e` job's own SQLite-in-CI pattern), no new tooling.
- **Skip create-first-user coverage entirely**: Rejected — leaves one of FR-002's five enumerated admin views permanently uncovered, undermining SC-001.

## Decision: Baseline environment determinism

**Decision**: Baselines are authoritative only when produced by one specific, single mechanism: a dedicated `update-visual-baselines` job in `.github/workflows/ci.yml`, triggered only by `workflow_dispatch` (a required `branch` input), running on `runs-on: ubuntu-24.04` — an explicit, dated runner label, not the floating `ubuntu-latest` alias, so the image doesn't drift under this workflow over time. The `visual-e2e` job (previous decision) is pinned to the same explicit `ubuntu-24.04` label, so baseline generation and baseline comparison always run on an identical, named environment. That job checks out the target branch, installs dependencies identically to `visual-e2e`, runs steps 1–3 from the previous decision with `--update-snapshots` appended to both Playwright invocations, and commits the regenerated PNGs directly back to that branch via `stefanzweifel/git-auto-commit-action` — **pinned to a specific commit SHA, not a floating tag**, since this is a third-party action running with `contents: write` — using the workflow's `GITHUB_TOKEN`, with `file_pattern` explicitly scoped to `e2e/visual.spec.ts-snapshots/ e2e/visual-first-run.spec.ts-snapshots/` (not the action's `.` default, which would stage every changed file in the workspace, including any stray run artifacts like `e2e/.visual-fixture.json` or a leftover job-local database file) — the one and only publication mechanism (no artifact-download-and-manually-commit alternative). `e2e/.visual-fixture.json` and the job-local SQLite database file are also added to `.gitignore`, alongside this repo's existing `e2e/.auth/`/`*.db` entries, as a second layer of protection against either ever being committed by accident. This is the only job in `ci.yml` that needs `contents: write`; it gets that via a job-level `permissions:` override, leaving the workflow's existing top-level `permissions: contents: read` default (and every other job) untouched, per this repo's existing least-privilege convention. `workflow_dispatch` can only be triggered by an authenticated user with write access to the repository, so a fork-originated PR cannot trigger this job — the correct behavior for a job holding `contents: write`. Running `npx playwright test --update-snapshots` on a developer's own machine is for local iteration/debugging only; its output is never committed.

**Rationale**: Font rendering, subpixel anti-aliasing, and OS-level rendering differences make cross-environment screenshot comparison inherently unreliable — a well-known Playwright limitation, not specific to this project. `ubuntu-latest` is a GitHub-maintained alias that can jump between entire major OS versions over its lifetime; `ubuntu-24.04` fixes that major-version jump, which is the drift this decision is actually trying to prevent. It is **not** a claim of byte-for-byte image immutability — GitHub does still periodically publish incremental updates to the `ubuntu-24.04` GA runner image itself (package/tool version bumps within the same OS release), so two runs months apart on `ubuntu-24.04` are not guaranteed pixel-identical either, only much closer than two runs on `ubuntu-latest` would be. If a baseline update ever appears to fail from environment drift alone (diffs with no corresponding code/content change), that is the residual risk this decision accepts for v1 rather than eliminates — see Alternatives Considered for the fuller-determinism option deferred for now.

**Alternatives considered**:
- **A pinned Playwright Docker image** (e.g. a specific `mcr.microsoft.com/playwright` tag pinned by digest), run identically in CI and locally: Playwright's own documented best practice, and the only way to get genuine image-level immutability rather than just "same OS major version" — would also let developers generate valid baselines locally. Not chosen for v1 because it requires introducing Docker as a new local-dev dependency this project doesn't otherwise have; `ubuntu-24.04` is a meaningfully better mitigation than the `ubuntu-latest` this repo's other jobs already use, at zero added tooling cost. Revisit this if `ubuntu-24.04` image updates ever actually cause a false-drift incident in practice.
- **Uploading regenerated PNGs as a downloadable artifact for a human to commit manually**: Rejected in favor of a direct commit-and-push — one concrete mechanism beats two documented-but-optional ones, and removes a manual step that's easy to skip or get wrong.
- **Reviewing CI's failure-diff artifact and manually re-creating a baseline PNG by hand**: Rejected — not a real workflow, just restates "someone eyeballs a diff," with no mechanism for actually producing the replacement file.

## Decision: Structured results format — Allure

**Decision**: Add `allure-playwright` as the reporter to **both** `playwright.config.ts` (the existing `chromium` config) and the new `playwright.visual.config.ts` (alongside existing `github`/`html` reporters in CI, and alongside `list` locally), configured to always run so every Playwright invocation appends to `allure-results/`. This is one of the two concrete, additive changes the existing `e2e` job/`playwright.config.ts` genuinely does need — it does not change any `chromium` test's behavior, only what the job also reports (the Isolation-model decision's "zero changes" language refers specifically to `chromium`'s test definitions and `e2e/global-setup.ts`, not to the reporter/CI-step tooling around them). Because `allure-playwright` appends to (rather than replaces) an existing `allure-results/` directory, each CI **job** clears that directory once, at the start of the job, before its *first* Playwright invocation — the existing `e2e` job clears it before running `chromium` (the second additive change to that job), and the new `visual-e2e` job (previous decision) clears it once before its first invocation (`visual-first-run`), deliberately *not* clearing it again before its second invocation (`visual`), so both projects' results land together in one combined `allure-results/` for that job — exactly mirroring how the `e2e` job's single artifact already covers everything `chromium` produces. Locally, `npm run test:e2e` (unchanged — still bare `playwright test`, implicitly using `playwright.config.ts`, see the Test-organization decision) gets the same one-clear-per-invocation treatment via a `pretest:e2e` npm script. For generating the human-browsable static report from `allure-results/`, use the `allure` npm package (Allure 3, TypeScript-based, runnable via `npx allure`) rather than the older `allure-commandline` package (Allure 2, requires a Java runtime) — avoids adding a Java toolchain to CI/local dev purely for report generation.

**Rationale**: Explicitly required by the source issue as the sole deliverable this feature must produce for a separate, already-filed roadmap issue (#16, the results dashboard) to consume later — issue #16 is explicitly out of scope for this feature, but its input format is not, since retrofitting a reporter later would mean re-running history that was never captured. `allure-playwright` is the standard, actively maintained adapter for this pairing; `@playwright/test`'s currently installed `^1.61.1` satisfies its `>=1.53.0` peer requirement.

**Alternatives considered**:
- **Playwright's own JSON reporter** (`--reporter=json`): Rejected — satisfies "machine-readable" but not the specific Allure-compatible shape the downstream dashboard issue is designed around; would require a translation step later.
- **JUnit XML reporter**: Rejected for the same reason — a different, less rich structured format than what Allure provides (no built-in screenshot/attachment linking the way Allure's model has).
- **`allure-commandline` (Allure 2, Java-based)**: Rejected in favor of the Node-based `allure` (Allure 3) package specifically to avoid a Java dependency this Node/TypeScript project otherwise has no need for.

## Decision: Dynamic-content masking approach

**Decision**: Use Playwright's built-in `mask` option on `toHaveScreenshot()` (an array of `Locator`s painted over with a solid box before comparison), applied only to genuinely *run-varying* regions: Payload's own auto-generated internal document IDs where visible (distinct from the fixture's fixed, human-chosen `visual-test-vehicle` slug — see below), any timestamp displays, and Payload admin's live "last updated" style fields if present in a covered view. The fixture's deterministic slug (`visual-test-vehicle`) and any other value `visual-setup.ts` sets to a fixed, known constant are deliberately **not** masked — they're stable by construction (per the fixture decision below), so leaving them visible in the screenshot comparison is itself a useful assertion: if a test somehow navigated to the wrong page or the routing broke, an un-masked, wrong slug in the rendered content would show up as a diff, whereas masking it would silently hide that failure. Because a `Locator` is bound to the specific `Page` it was created from, masks are built fresh per test via a helper function (`getVisualMasks(page, view)` in `e2e/helpers.ts`) rather than defined once as a module-level constant — a `Locator` created against one test's `page` instance cannot be reused against another test's `page`.

**Rationale**: Native to the same `toHaveScreenshot()` API already chosen, requires no extra dependency, and is the documented Playwright-recommended pattern for exactly this problem (FR-004). Concrete masked regions per page are enumerated during implementation (`tasks.md`) after inspecting each covered page/view for what's actually dynamic — this research file records the mechanism, not the exhaustive per-page list, since that's implementation detail appropriately deferred to task breakdown.

**Alternatives considered**:
- **Seeding fully deterministic fixture data so nothing is dynamic**: Considered complementary, not a substitute — the admin dashboard and list views may still show Payload-internal auto-generated timestamps/IDs regardless of how deterministic the seed data is, so masking is still needed as a backstop even with deterministic fixtures.
- **A single module-level `Locator[]` constant reused across tests**: Rejected once identified as invalid — `Locator`s are page-scoped in Playwright's API, so this would throw or silently mask nothing for any page other than the one it was first created against.

## Decision: Admin auth for visual tests

**Decision**: `e2e/visual-setup.ts` (the `visual-e2e` job's own setup script — see the Isolation-model decision above) creates the admin user and writes `AUTH_STATE_PATH` using the same login/create-first-user branching logic `e2e/global-setup.ts` already has (duplicated into the new script rather than shared, since `global-setup.ts` is a Playwright `globalSetup` hook tied to the `e2e` job's config and `visual-setup.ts` is a plain script step in a different job — the two run in fundamentally different harnesses, so extracting a shared function both call is a reasonable, small refactor to consider *during implementation*, but isn't required for correctness). The `visual` project's authenticated tests then apply `test.use({ storageState: AUTH_STATE_PATH })` exactly like `e2e/admin.spec.ts` already does, except for `/admin/login` (don't apply `storageState` — must render logged-out) and `/admin/create-first-user`, which is covered separately by `visual-first-run` running before `visual-setup.ts` executes at all (see Isolation-model decision).

**Rationale**: Constitution Principle IV requires verifying access empirically rather than assuming — reusing the exact login/create-first-user logic `global-setup.ts` already has (proven to work) for `visual-setup.ts` satisfies that without inventing new auth logic. Constitution Principle VI (no premature abstraction) is why extracting a shared helper is left as an optional implementation-time refactor rather than mandated here — two small scripts with duplicated logic is simpler to reason about right now than introducing a shared module with two different callers (a Playwright `globalSetup` hook vs. a plain CI-step script) that have different execution contexts.

## Decision: Deterministic fixture data for public-site visual tests

**Decision**: The shared Make/Model/Vehicle fixture used by the public-site visual tests (landing, listing, detail, admin edit-view) is created once by `visual-setup.ts` with a fixed, deterministic slug (e.g. `visual-test-vehicle`), via the existing `createMake`/`createModel`/`createPublishedVehicle` helpers, unconditionally (no upsert/idempotency logic needed) — because the `visual-e2e` job's database is freshly created for that job run (previous decision), there is no pre-existing data to collide with or accumulate alongside. The un-filtered listing snapshot (`/en/vehicles`, no filters) shows exactly this one vehicle, deterministically, on every run.

**Rationale**: An earlier draft of this decision tried to solve determinism with an idempotent "find-or-create" helper (`getOrCreateVisualFixture`) reused across repeated runs against a *shared* database — review correctly pointed out that even a stable, reused fixture doesn't stop *other* vehicles (from the functional suite's own fixtures, or prior manual testing) from also appearing in an un-filtered listing query, so the listing snapshot could still change for reasons unrelated to this one fixture. Job-level database isolation removes the need for idempotency logic entirely: a fresh database has nothing to collide with, so a plain unconditional create is both simpler and more genuinely deterministic than a lookup-or-create against shared state ever could be. The fixture's ID/slug are still captured once in a shared scope (e.g. written to a small JSON file by `visual-setup.ts`, or exported via an environment variable, and read by `e2e/visual.spec.ts`'s tests) so the listing, detail, and collection-edit-view tests all reference the same seeded Vehicle.

**Alternatives considered**:
- **An idempotent "find-or-create" fixture reused across runs against a shared database** (the rejected earlier draft): Doesn't actually isolate the listing snapshot from other database content — see Rationale.
- **Leaving `createPublishedVehicle` as-is with its `Date.now()`-suffixed random slugs, called fresh each `visual-e2e` job run**: This is actually fine now that the database is job-local and thrown away between CI runs — a fixed slug isn't strictly required for correctness anymore, but is kept anyway since a stable, human-readable slug (`visual-test-vehicle`) makes `e2e/visual.spec.ts` easier to read and debug than a timestamp-suffixed one, at zero extra cost.
