# Phase 0 Research: Visual/UI Regression Testing with Allure Reporting

All items below were determined from the source issue's explicit proposal plus inspection of this repo's existing `playwright.config.ts`, `.github/workflows/ci.yml`, and `e2e/*.spec.ts` conventions — no items remained `NEEDS CLARIFICATION` after spec authoring, so this file records the reasoning behind each Technical Context decision rather than resolving open questions.

## Decision: Visual comparison mechanism

**Decision**: Use Playwright's native `expect(page).toHaveScreenshot()` / `expect(locator).toHaveScreenshot()`.

**Rationale**: Already bundled with `@playwright/test`, which this project already depends on and already uses for all other e2e coverage. Produces pixel-diff PNGs on failure automatically, integrates with the existing `html`/`github` reporters, and needs no new test runner or CI step beyond what already exists for the functional suite. The source issue explicitly calls this out as the preferred approach over adopting a separate framework.

**Alternatives considered**:
- **Percy / Chromatic (paid SaaS)**: Rejected per the source issue and spec Assumptions — external cost/vendor dependency for a capability Playwright already provides natively.
- **A custom pixel-diff script (e.g., `pixelmatch` invoked manually)**: Rejected — reinvents what `toHaveScreenshot()` already does, with worse reporter/CI integration.

## Decision: Test organization — separate Playwright `project`

**Decision**: Add `visual` and `visual-first-run` entries to the `projects` array in `playwright.config.ts`, with visual assertions in new `e2e/visual.spec.ts`/`e2e/visual-first-run.spec.ts` files (not mixed into `admin.spec.ts`/`public.spec.ts`). Each project's `testMatch` scopes it to only its own spec file, and the existing `chromium` project gets `testIgnore` for **both** new spec files, so a bare `npx playwright test` (no `--project` flag) run by anyone unfamiliar with this feature's job-separation model (see Isolation-model decision) can't accidentally run `visual-first-run` outside its dedicated fresh-database job and get a false pass/fail from stale state. Because of that same job separation, `package.json`'s `test:e2e` script changes from bare `playwright test` to `playwright test --project=chromium` — this is a behavior-*preserving* change for the functional suite itself (identical tests, identical results) that exists solely so the script's scope stays explicit once other projects exist; a new `test:e2e:visual` script (`playwright test --project=visual`) covers the `visual` project, and `visual-first-run` is documented as CI-only via the `visual-e2e` job, not wired to any local npm script (see quickstart.md).

**Rationale**: Playwright projects can be filtered independently, get separate result grouping in reporters (including Allure, which reports Playwright project as a distinct dimension), and can have distinct `use` config (e.g., forcing consistent `deviceScaleFactor`/color-scheme for visual tests specifically) without affecting the `chromium` functional project. This directly satisfies FR-005 (distinct, separately-triageable group) using a mechanism already native to the tool in use, consistent with Constitution Principle VI (no premature abstraction).

**Alternatives considered**:
- **A separate Playwright config file** (`playwright.visual.config.ts`): Rejected — duplicates `webServer`/`baseURL` config that already lives in the one config file; a second/third project entry is simpler and keeps one source of truth.
- **Tagging tests with `test.describe` + grep filters** (no new project): Rejected — grep-based filtering is more fragile (relies on naming discipline) and doesn't get separate reporter grouping the way `project` does.
- **Leaving `chromium` without `testIgnore` for the new spec files, relying on `test:e2e`'s explicit `--project=chromium` alone**: Rejected — a defense-in-depth choice, not strictly required once `test:e2e` is scoped explicitly, but cheap insurance against a bare `playwright test` invocation (e.g. run manually by someone debugging, or a future CI change) silently picking up projects it shouldn't.

## Decision: Isolation model — visual tests get their own CI job and database

**Decision**: `visual` and `visual-first-run` (Playwright projects, per the next decision) run in a **new, dedicated CI job** (`visual-e2e` in `.github/workflows/ci.yml`), entirely separate from the existing `e2e` job, against a **freshly created, job-local SQLite database file** (a distinct `DATABASE_URI` env var, not shared with the `e2e` job) and its own `npm run dev` server instance. This job does **not** touch `e2e/global-setup.ts` or the `chromium` project in any way — those stay exactly as they are today. Within `visual-e2e`, in order:
1. `npx playwright test --project=visual-first-run` runs first, directly, against the still-empty fresh database — no admin user exists yet, so `/admin/create-first-user` genuinely renders its first-run form rather than redirecting.
2. A small setup script, `e2e/visual-setup.ts` (run as a plain step in the CI job — a script, not a Playwright `globalSetup`), then: creates the admin user and writes `AUTH_STATE_PATH` (the same login/create-first-user branching logic `e2e/global-setup.ts` already has), seeds `SiteSettings` with the same fields `global-setup.ts` seeds today (shop name, contact email/phone, address, Instagram link — so Header/Footer/About render real content, not empty CMS fields), and creates the one deterministic Make/Model/Vehicle fixture (`getOrCreateVisualFixture`, see below).
3. `npx playwright test --project=visual` then runs against this now-seeded, still job-isolated database.

**Rationale**: An earlier draft of this decision tried to reuse the existing shared `e2e` job/database via Playwright's project-dependencies model (a `admin-setup` project that `chromium`/`visual` depend on, with `visual-first-run` opting out). Review correctly identified two problems that model doesn't actually solve: (1) it cannot *guarantee* `visual-first-run` sees an empty database — the absence of a declared dependency doesn't stop some other project from having already created a user, it only stops that specific dependency edge from doing so — and (2) even with a deterministic fixture, the shared database still contains whatever the `chromium` project's functional tests (and prior runs) leave behind, so `/en/vehicles` (the un-filtered listing snapshot) would still show a non-deterministic set of vehicles. A dedicated job with its own fresh database eliminates both problems by construction: nothing else ever writes to it, so "empty until step 2 creates a user" and "contains exactly the one seeded vehicle" are both structurally true, not merely likely. This also means the existing `e2e` job and `chromium` project require **zero changes** to support this feature — the strongest possible form of FR-010/SC-006 ("existing functional tests unaffected"), since nothing about their configuration or shared state changes at all. The extra cost — a second `npm run dev`/database boot in CI — is cheap; the existing `e2e` job already demonstrates this pattern takes seconds, not minutes.

**Alternatives considered**:
- **Project-dependencies within the existing shared `e2e` job/database** (the rejected earlier draft): Doesn't actually guarantee the empty-DB precondition or listing-page determinism — see Rationale.
- **A dedicated Docker container per test run**: Rejected as disproportionate — a second CI job with a second SQLite file uses infrastructure this project already has (the `e2e` job's own SQLite-in-CI pattern), no new tooling.
- **Skip create-first-user coverage entirely**: Rejected — leaves one of FR-002's five enumerated admin views permanently uncovered, undermining SC-001.

## Decision: Baseline environment determinism

**Decision**: Baselines are authoritative only when produced by one specific, single mechanism: a dedicated `update-visual-baselines` job in `.github/workflows/ci.yml`, triggered only by `workflow_dispatch` (a required `branch` input), running on `runs-on: ubuntu-24.04` — an explicit, dated runner label, not the floating `ubuntu-latest` alias, so the image doesn't drift under this workflow over time. The `visual-e2e` job (previous decision) is pinned to the same explicit `ubuntu-24.04` label, so baseline generation and baseline comparison always run on an identical, named environment. That job checks out the target branch, installs dependencies identically to `visual-e2e`, runs steps 1–3 from the previous decision with `--update-snapshots` appended to both Playwright invocations, and commits the regenerated PNGs directly back to that branch via `stefanzweifel/git-auto-commit-action` using the workflow's `GITHUB_TOKEN` — the one and only publication mechanism (no artifact-download-and-manually-commit alternative). This is the only job in `ci.yml` that needs `contents: write`; it gets that via a job-level `permissions:` override, leaving the workflow's existing top-level `permissions: contents: read` default (and every other job) untouched, per this repo's existing least-privilege convention. `workflow_dispatch` can only be triggered by an authenticated user with write access to the repository, so a fork-originated PR cannot trigger this job — the correct behavior for a job holding `contents: write`. Running `npx playwright test --update-snapshots` on a developer's own machine is for local iteration/debugging only; its output is never committed.

**Rationale**: Font rendering, subpixel anti-aliasing, and OS-level rendering differences make cross-environment screenshot comparison inherently unreliable — a well-known Playwright limitation, not specific to this project. `ubuntu-latest` is a GitHub-maintained alias whose underlying image is periodically updated, so two jobs both saying `ubuntu-latest` are not guaranteed to be identical *over time* (only at a given instant) — pinning both the update-workflow and the `visual-e2e` job to the same explicit dated label (`ubuntu-24.04`) removes that drift risk. This intentionally leaves the pre-existing `e2e`/`test`/`typecheck`/`build` jobs on `ubuntu-latest`, unchanged — those aren't part of this feature's scope, and pinning them is an orthogonal change outside what this feature needs (the only invariant this feature requires is that baseline generation and baseline comparison agree with *each other*, which holds regardless of what label the unrelated jobs use). The source issue explicitly names this determinism requirement and asks that it be documented the same way this repo already documents its `tsx`/`@next/env` gotcha in the README.

**Alternatives considered**:
- **A pinned Playwright Docker image**, run identically in CI and locally: Playwright's own documented best practice, and would let developers generate valid baselines locally too. Not chosen for v1 because it requires introducing Docker as a new local-dev dependency this project doesn't otherwise have; a pinned runner label achieves the needed determinism without it.
- **Uploading regenerated PNGs as a downloadable artifact for a human to commit manually**: Rejected in favor of a direct commit-and-push — one concrete mechanism beats two documented-but-optional ones, and removes a manual step that's easy to skip or get wrong.
- **Reviewing CI's failure-diff artifact and manually re-creating a baseline PNG by hand**: Rejected — not a real workflow, just restates "someone eyeballs a diff," with no mechanism for actually producing the replacement file.

## Decision: Structured results format — Allure

**Decision**: Add `allure-playwright` as the reporter (alongside existing `github`/`html` reporters in CI, and alongside `list` locally), configured to always run so every Playwright invocation appends to `allure-results/`. Because `allure-playwright` appends to (rather than replaces) an existing `allure-results/` directory, each CI **job** clears that directory once, at the start of the job, before its *first* Playwright invocation — the existing `e2e` job clears it before running `chromium`, and the new `visual-e2e` job (previous decision) clears it once before its first invocation (`visual-first-run`), deliberately *not* clearing it again before its second invocation (`visual`), so both projects' results land together in one combined `allure-results/` for that job — exactly mirroring how the `e2e` job's single artifact already covers everything `chromium` produces. Locally, `npm run test:e2e` (now scoped to just `--project=chromium`, see the Test-organization decision) gets the same one-clear-per-invocation treatment via a `pretest:e2e` npm script. For generating the human-browsable static report from `allure-results/`, use the `allure` npm package (Allure 3, TypeScript-based, runnable via `npx allure`) rather than the older `allure-commandline` package (Allure 2, requires a Java runtime) — avoids adding a Java toolchain to CI/local dev purely for report generation.

**Rationale**: Explicitly required by the source issue as the sole deliverable this feature must produce for a separate, already-filed roadmap issue (#16, the results dashboard) to consume later — issue #16 is explicitly out of scope for this feature, but its input format is not, since retrofitting a reporter later would mean re-running history that was never captured. `allure-playwright` is the standard, actively maintained adapter for this pairing; `@playwright/test`'s currently installed `^1.61.1` satisfies its `>=1.53.0` peer requirement.

**Alternatives considered**:
- **Playwright's own JSON reporter** (`--reporter=json`): Rejected — satisfies "machine-readable" but not the specific Allure-compatible shape the downstream dashboard issue is designed around; would require a translation step later.
- **JUnit XML reporter**: Rejected for the same reason — a different, less rich structured format than what Allure provides (no built-in screenshot/attachment linking the way Allure's model has).
- **`allure-commandline` (Allure 2, Java-based)**: Rejected in favor of the Node-based `allure` (Allure 3) package specifically to avoid a Java dependency this Node/TypeScript project otherwise has no need for.

## Decision: Dynamic-content masking approach

**Decision**: Use Playwright's built-in `mask` option on `toHaveScreenshot()` (an array of `Locator`s painted over with a solid box before comparison), applied to known-dynamic regions: seeded record IDs/slugs where visible in the UI, any timestamp displays, and Payload admin's live "last updated" style fields if present in a covered view. Because a `Locator` is bound to the specific `Page` it was created from, masks are built fresh per test via a helper function (`getVisualMasks(page, view)` in `e2e/helpers.ts`) rather than defined once as a module-level constant — a `Locator` created against one test's `page` instance cannot be reused against another test's `page`.

**Rationale**: Native to the same `toHaveScreenshot()` API already chosen, requires no extra dependency, and is the documented Playwright-recommended pattern for exactly this problem (FR-004). Concrete masked regions per page are enumerated during implementation (`tasks.md`) after inspecting each covered page/view for what's actually dynamic — this research file records the mechanism, not the exhaustive per-page list, since that's implementation detail appropriately deferred to task breakdown.

**Alternatives considered**:
- **Seeding fully deterministic fixture data so nothing is dynamic**: Considered complementary, not a substitute — the admin dashboard and list views may still show Payload-internal auto-generated timestamps/IDs regardless of how deterministic the seed data is, so masking is still needed as a backstop even with deterministic fixtures.
- **A single module-level `Locator[]` constant reused across tests**: Rejected once identified as invalid — `Locator`s are page-scoped in Playwright's API, so this would throw or silently mask nothing for any page other than the one it was first created against.

## Decision: Admin auth for visual tests

**Decision**: `e2e/visual-setup.ts` (the `visual-e2e` job's own setup script — see the Isolation-model decision above) creates the admin user and writes `AUTH_STATE_PATH` using the same login/create-first-user branching logic `e2e/global-setup.ts` already has (duplicated into the new script rather than shared, since `global-setup.ts` is a Playwright `globalSetup` hook tied to the `e2e` job's config and `visual-setup.ts` is a plain script step in a different job — the two run in fundamentally different harnesses, so extracting a shared function both call is a reasonable, small refactor to consider *during implementation*, but isn't required for correctness). The `visual` project's authenticated tests then apply `test.use({ storageState: AUTH_STATE_PATH })` exactly like `e2e/admin.spec.ts` already does, except for `/admin/login` (don't apply `storageState` — must render logged-out) and `/admin/create-first-user`, which is covered separately by `visual-first-run` running before `visual-setup.ts` executes at all (see Isolation-model decision).

**Rationale**: Constitution Principle IV requires verifying access empirically rather than assuming — reusing the exact login/create-first-user logic `global-setup.ts` already has (proven to work) for `visual-setup.ts` satisfies that without inventing new auth logic. Constitution Principle VI (no premature abstraction) is why extracting a shared helper is left as an optional implementation-time refactor rather than mandated here — two small scripts with duplicated logic is simpler to reason about right now than introducing a shared module with two different callers (a Playwright `globalSetup` hook vs. a plain CI-step script) that have different execution contexts.

## Decision: Deterministic fixture data for public-site visual tests

**Decision**: The shared Make/Model/Vehicle fixture used by the public-site visual tests (landing, listing, detail, admin edit-view) is created once by `visual-setup.ts` with a fixed, deterministic slug (e.g. `visual-test-vehicle`), via the existing `createMake`/`createModel`/`createPublishedVehicle` helpers, unconditionally (no upsert/idempotency logic needed) — because the `visual-e2e` job's database is freshly created for that job run (previous decision), there is no pre-existing data to collide with or accumulate alongside. The un-filtered listing snapshot (`/en/vehicles`, no filters) shows exactly this one vehicle, deterministically, on every run.

**Rationale**: An earlier draft of this decision tried to solve determinism with an idempotent "find-or-create" helper (`getOrCreateVisualFixture`) reused across repeated runs against a *shared* database — review correctly pointed out that even a stable, reused fixture doesn't stop *other* vehicles (from the functional suite's own fixtures, or prior manual testing) from also appearing in an un-filtered listing query, so the listing snapshot could still change for reasons unrelated to this one fixture. Job-level database isolation removes the need for idempotency logic entirely: a fresh database has nothing to collide with, so a plain unconditional create is both simpler and more genuinely deterministic than a lookup-or-create against shared state ever could be. The fixture's ID/slug are still captured once in a shared scope (e.g. written to a small JSON file by `visual-setup.ts`, or exported via an environment variable, and read by `e2e/visual.spec.ts`'s tests) so the listing, detail, and collection-edit-view tests all reference the same seeded Vehicle.

**Alternatives considered**:
- **An idempotent "find-or-create" fixture reused across runs against a shared database** (the rejected earlier draft): Doesn't actually isolate the listing snapshot from other database content — see Rationale.
- **Leaving `createPublishedVehicle` as-is with its `Date.now()`-suffixed random slugs, called fresh each `visual-e2e` job run**: This is actually fine now that the database is job-local and thrown away between CI runs — a fixed slug isn't strictly required for correctness anymore, but is kept anyway since a stable, human-readable slug (`visual-test-vehicle`) makes `e2e/visual.spec.ts` easier to read and debug than a timestamp-suffixed one, at zero extra cost.
